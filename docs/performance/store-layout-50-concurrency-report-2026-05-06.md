# layout_map_label_studio 50 并发压测报告

- 日期：2026-05-06
- 项目：`layout_map_label_studio`
- 测试目标：评估 50 并发访问下的基础可用性与资源消耗（CPU / Memory / I/O / Network）
- 测试结论：在本次本地环境测试中，项目能够稳定承载 50 并发访问，两个已测入口均 **0 失败请求**。

## 测试环境

- 操作系统：macOS
- 机器：Apple M4
- 逻辑 CPU 数：10
- 服务运行方式：`uWSGI`
- `uWSGI` worker 数：4
- 数据库：SQLite
- 网络：本机回环 `127.0.0.1` / `lo0`
- 认证方式：已登录 session
- 说明：
  - 本次测试未走 Docker / Nginx / PostgreSQL 生产链路。
  - 因此本报告适合用于评估 **应用本身在本地单机环境下的 50 并发承载能力**，不应直接等同于线上容量承诺。

## 测试方法

### 压测入口

本次选择了两个已登录后的典型入口进行测试：

1. `GET /api/projects/`
2. `GET /projects/`

### 并发参数

- 压测工具：ApacheBench (`ab`)
- 并发数：`50`
- 请求总数：`1000`
- Keep-Alive：开启（`-k`）

### 资源采样方法

- CPU / Memory：通过 `psutil` 对 `uWSGI` 进程组采样
- Network：统计本机 `lo0` 网卡在测试窗口内的字节增量
- I/O：
  - 优先采集进程级 I/O 计数
  - 由于 macOS 当前环境下未拿到可靠的进程级 I/O 字节计数，因此本报告主要采用 **系统级磁盘 I/O 增量** 作为参考

## 总结结论

### 结论摘要

- **50 并发访问 `GET /api/projects/`：稳定，通过，0 失败**
- **50 并发访问 `GET /projects/`：稳定，通过，0 失败**
- 当前测试中：
  - CPU 未打满
  - 内存维持在约 `0.7 ~ 1.05 GiB`
  - 页面路由的网络流量明显高于 API
  - 磁盘 I/O 不是主要瓶颈

### 结论边界

本次压测更接近：

- 项目列表页面访问
- 项目列表 API 查询

不等同于：

- 50 人同时标注
- 50 人同时请求下一条任务
- 50 人同时保存标注
- 大型 store layout JSON / 图片资源 / 标注保存链路的生产级压力测试

## 对比分析

| 维度     | `/api/projects/` | `/projects/` | 说明                       |
| -------- | ---------------: | -----------: | -------------------------- |
| 吞吐     |     158.19 req/s | 119.20 req/s | API 吞吐更高               |
| 平均响应 |        316.07 ms |    419.45 ms | 页面更慢                   |
| CPU 平均 |          334.71% |      145.72% | API 端更吃 CPU             |
| 内存平均 |       876.12 MiB |   723.39 MiB | API 端平均内存更高         |
| 网络总量 |        26.29 MiB |   164.87 MiB | 页面返回更大，网络明显更高 |
| 失败请求 |                0 |            0 | 两者都稳定                 |

### 观察

1. `/api/projects/` 的 CPU 消耗高于 `/projects/`
   - 说明 API 侧序列化、查询、权限链路可能更偏 CPU 密集。

2. `/projects/` 的网络流量显著更高
   - 这是预期现象，HTML 页面响应体远大于项目列表 API。

3. 两组测试下内存峰值都在约 `1.0 GiB` 左右
   - 说明 50 并发项目列表访问并未出现明显失控。

4. 两组测试均未出现失败请求
   - 说明当前测试入口下 50 并发的稳定性是合格的。

## 风险与限制

### 1. 非生产链路

本次不是以下完整生产部署：

- Nginx
- PostgreSQL
- Docker / Compose
- 真实公网访问

因此：

- 不能直接把结论等同于线上 SLA
- 但可以说明应用本身在本地单机下没有明显 50 并发问题

### 2. 未覆盖真实标注热点接口

本次未测：

- `/api/projects/{id}/tasks/`
- `/api/projects/{id}/next`
- 标注保存接口
- store layout 专用页面和实际标注流程

所以本报告不应被解读为：

- “50 人同时在线完整标注流程已验证通过”

更准确的说法是：

- “50 并发访问项目列表相关入口已验证通过”

### 3. 进程级 I/O 统计限制

在当前 macOS + Python/uWSGI 环境下：

- 未能得到可靠的进程级 I/O 字节数据

因此报告中的 I/O 结论主要参考：

- 系统级磁盘 I/O 增量

## 推荐下一步

如果需要更接近真实生产和真实业务负载，建议继续补测：

1. **生产近似部署**
   - Nginx + uWSGI + PostgreSQL
   - 与上线参数一致的 worker / timeout / DB 连接配置

2. **真实热点接口**
   - `/api/projects/{id}/tasks/`
   - `/api/projects/{id}/next`
   - 标注保存接口

3. **真实业务数据**
   - store layout 项目
   - 真实任务数量
   - 真实大 JSON / 真实图片资源

4. **更接近“50 人同时在线标注”的流程压测**
   - 登录
   - 打开项目
   - 请求下一条任务
   - 保存标注
   - 重复操作

## 最终结论

在本次测试条件下，`layout_map_label_studio` 对于以下两类访问：

- `GET /api/projects/`
- `GET /projects/`

均可以稳定承载 **50 并发请求**，且：

- 失败请求为 `0`
- CPU 未打满
- 内存维持在可控范围内
- 磁盘 I/O 不是主要瓶颈
- 页面访问的网络流量明显高于 API

因此可以得出阶段性结论：

> 在当前本地单机环境下，项目列表相关入口支持 50 并发访问没有明显问题。

但若要进一步回答：

> “能否支撑 50 人同时在线完成真实 store layout 标注工作流？”

还需要继续补做 **任务获取、标注保存、真实项目数据、生产近似部署** 的专项压测。
